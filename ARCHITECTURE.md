# Architecture Guide

This is the developer-facing companion to [README.md](README.md) (what this agent reports, how to deploy it, the full Managed Configuration field reference). This document explains how the codebase itself is put together — for an engineer picking this repo up for the first time.

This repo ships **two separate binaries, two separate toolchains, no shared code between them**: a Go daemon (`main.go` + the flat `*_macos.go` files at repo root) that runs as root via a `LaunchDaemon`, and a Swift/SwiftUI menu bar app (`MenuBarApp/`) that runs unprivileged, per signed-in console user, via a `LaunchAgent`. They never talk to each other directly — the daemon has no idea the menu bar app exists, and vice versa — they communicate exclusively through a small shared directory on disk (§3). This split exists because the daemon needs root (disk-encryption/firewall/Secure Boot-equivalent checks, writing to a system LaunchDaemon path) while a menu bar icon fundamentally has to run in a logged-in user's own GUI session — no single process can be both at once on macOS.

Both companion repos — this one and [`applivery-soar-agent-windows`](https://github.com/raulcnadal/applivery-soar-agent-windows) — report into the same SOAR backend (`applivery-soar`, see that repo's own `ARCHITECTURE.md` §9) through the same two device-facing endpoints, so this file focuses on the macOS-specific half of that contract; the backend side is documented once, there.

## 1. The Go daemon (repo root, `package main`)

`main.go` is a thin entry point: starts `runAgentLoop` (`telemetry_macos.go`) in a goroutine, then blocks on `SIGINT`/`SIGTERM`. Every other file is flat in `package main` (no `internal/` split like the Windows agent has — there was never enough macOS-specific surface area to justify one):

- **`config.go`** — `Config` struct, decoded from the Managed Configuration file at `/Library/Preferences/es.mi-labs.soar.agent.json` (an MDM-pushed Custom Settings payload, README.md's full field table). `LoadConfig`/`loadConfigQuiet` apply defaults for anything the file omits; `IsConfigured()` requires `WorkspaceSlug` plus either `ReportSecret` or `BootstrapToken` (an mTLS-only deployment with no legacy secret at all is fully supported, not a partial config).
- **`telemetry_macos.go`** — `runAgentLoop`: a `time.Ticker` on `Config.IntervalSec` (default 3600s) drives the actual report cycle (`gatherAndReport`, reloading config fresh every tick so a Managed Configuration push takes effect without a restart), plus a second, much tighter `triggerPollInterval` (2s) ticker that watches for the menu bar app's trigger flags (§3) and for `remoteIntervalSec` (a SOAR-side override delivered piggybacked on the Event Watches poll, letting an admin shorten the effective interval fleet-wide without touching Managed Configuration at all — `maybeResetTicker`).
- **`security_macos.go`** — the actual security-signal collectors: `GetFileVaultStatus` (`fdesetup status`), `GetFirewallStatus` (`socketfilterfw --getglobalstate`, parsed for `State = 1` — see this file's own doc comment for the real-device debugging story behind that exact substring match), XProtect (always reported `true` — ships enabled by default on every supported macOS version, no tamper-detection attempted).
- **`apps_macos.go`** — installed-application inventory (`system_profiler SPApplicationsDataType`), reported separately via `POST /api/device-data/report-apps`.
- **`customchecks_macos.go`** — the five Custom Device Check types (process running via `pgrep`, `launchctl` job status, plist/file value via `plutil`, installed-app-and-version, arbitrary shell command), polled from `GET /api/device-data/custom-checks?platform=macos` once per report cycle and returned inline in the next report's `customCheckResults`. Same JSON contract as the Windows agent's independent implementation (`customchecks_windows.go`) — see the backend's `customChecks.service.ts` module doc for the shared design.
- **`eventwatch_macos.go`** — Event-Driven Detection: `fsnotify` (kqueue-based on Darwin, pure Go, no CGo) watches for filesystem changes matching admin-defined watch rules polled from `GET /api/device-data/event-watches?platform=macos`; a local debounce collapses a burst of matching events into one `POST /api/device-data/event-notify` call once things go quiet, rather than one call per raw filesystem event.
- **`mtls_macos.go`** — mTLS agent identity: local ECDSA keypair generation (private key never leaves the device), one-time CSR-based registration against `POST /api/device-mtls/register` using the Managed-Configuration-delivered Global Bootstrap Token, and a self-sustaining renewal loop that never needs the bootstrap token again after first enrollment. File-based keystore (root-owned, `0600`, under this daemon's own state directory) rather than Keychain — a deliberate simplification matching the Windows agent's own Certificate Store simplification, justified by this daemon already running as root for every other privileged operation it performs.
- **`status_macos.go`** — `fetchAgentStatus`, a thin client for `GET /api/device-data/agent-status` (compliance/risk summary for this specific device), consumed by `agentstatus_macos.go` to build the status cache below.
- **`agentstatus_macos.go`** — the daemon's half of the file-based IPC contract with the menu bar app (§3): `AgentStatusPolicy`/`AgentStatusViolation`/`AgentStatusCompliance`/`AgentStatusDevice` structs, JSON-tagged, written to `status.json` after every report cycle. **The JSON tags here must stay in lockstep with `MenuBarApp/Sources/AppliverySOARMenuBar/StatusCache.swift`** — Swift's `Codable` throws `DecodingError.keyNotFound` on a missing key for any *non-Optional* property (unlike Go's `encoding/json`, which silently zero-values a missing field), so a Go field tagged `omitempty` must be mirrored as `Optional` (`T?`) on the Swift side, never a default value, or the whole document fails to decode the moment that field is actually omitted — a real bug this repo shipped and fixed once already (menu bar stuck on "Waiting for the first report" despite a perfectly valid `status.json` on disk, because `compliant` was `Bool = false` instead of `Bool?` opposite an `omitempty bool` in Go).

Every file above carries a `//go:build !windows` tag — harmless here (this repo only ever builds `GOOS=darwin`), but keeps the file unambiguous if it's ever diffed side-by-side against its Windows counterpart.

## 2. The Swift menu bar app (`MenuBarApp/`)

A **plain Swift Package** (`Package.swift`, `swift-tools-version:5.9`, `.executableTarget`), not a hand-authored `.xcodeproj`/`.pbxproj` — a project file is a fragile, largely-opaque binary-ish format to author and review without Xcode itself actually open, whereas `Package.swift` plus plain `.swift` files are as reviewable/diffable as any other source in this repo. `swift build` on the `macos-latest` CI runner (§5) is this target's compile verification, the same role `go build` plays for the daemon — this project has no local macOS/Xcode toolchain anywhere else, by design (see README's own "CI-verified, like the Go agents" framing).

Targets macOS 12 (Monterey) via a hand-rolled `NSStatusItem` + custom `NSPanel`, deliberately *not* the newer SwiftUI `MenuBarExtra` API (which would force a macOS 13+ floor) or `NSPopover` (tried and abandoned — see `StatusPanel.swift`'s own doc comment: `NSPopover`'s anchor-positioning math has known, hard-to-predict gap bugs for accessory/`LSUIElement` apps that two rounds of targeted fixes couldn't close; a custom panel computes its own screen position directly instead of relying on `NSPopover` internals).

Files, `MenuBarApp/Sources/AppliverySOARMenuBar/`:

- **`main.swift`** / **`AppDelegate.swift`** — app entry, `NSStatusItem` setup, the panel open/close logic (`togglePanel`/`openPanel`/`closePanel`), an `NSEvent` global monitor standing in for `NSPopover`'s built-in "close on outside click" behavior (no direct `NSPanel` equivalent), and the `UNUserNotificationCenterDelegate` conformance that forces compliance-transition/Force-report/Force-evaluate banners to display even while this app is itself the frontmost/active app (`UNUserNotificationCenter`'s default behavior otherwise suppresses banners for the frontmost app).
- **`StatusPanel.swift`** — the custom borderless `NSPanel` itself: rounded-card-plus-speech-bubble-arrow shape via a `CAShapeLayer` mask, `.nonactivatingPanel` so it never steals focus from whatever app was frontmost, and window `level = .floating` (deliberately *not* `.popUpMenu`, which this used until a real-device report showed it sitting high enough to render notification banners behind an open panel — `.floating` plus `collectionBehavior: .fullScreenAuxiliary` is Apple's own documented combination for a panel that still needs to stay above another app's full-screen window, which was `.popUpMenu`'s original justification).
- **`StatusStore.swift`** / **`StatusCache.swift`** — `StatusStore` is the `ObservableObject` driving the SwiftUI card (60s refresh loop plus an explicit `refresh()` on every panel open, so the card is never more than one report cycle stale); `StatusCache.swift` holds the `Codable` mirror of the daemon's `agentstatus_macos.go` structs (§1) and `StatusCacheStore.read()`, which treats any read/decode failure as `nil` rather than throwing — an empty "Waiting for the first report" state, not a crash, is the correct response to "the daemon hasn't written anything yet."
- **`StatusCardView.swift`** / **`CardSizing.swift`** — the actual SwiftUI card UI and its width/height-fitting logic (recomputed fresh every time the panel opens, since the row count varies with how many policies apply to this device).
- **`NotificationManager.swift`** — thin `UNUserNotificationCenter` wrapper (`requestAuthorization`, `postComplianceAlert`), the macOS equivalent of the Windows tray's `Shell_NotifyIconW`/`NIF_INFO` balloon calls. Same title/body strings as the Windows tray's own `triggerForceReport`/`triggerForceEvaluate`, so a mixed Windows/macOS fleet sees identically-worded alerts everywhere this fires.
- **`FontLoader.swift`** / **`DesignTokens.swift`** / **`BannerImage.swift`** — bundled-font registration (three Outfit weights, `Resources/Fonts`, so the card reads identically to the Windows tray's own card instead of silently falling back to San Francisco) and the header banner image (`Resources/Images/applivery-banner.png`, rasterized offline from `assets/applivery-bp-login.svg` via `cairosvg` + an ImageMagick `-trim` autocrop — see `Package.swift`'s resource-rule comment).
- **`IPCPaths.swift`** — this app's half of the shared-directory contract (§3).
- **`DebugLog.swift`** — a small on-disk log the panel-open/close diagnostics write to, for troubleshooting on a real device with no attached debugger.
- **`Info.plist`** — `LSUIElement = true` (no Dock icon, no Cmd+Tab entry — the menu bar icon is this app's only UI surface), not sandboxed (reads the root-owned shared IPC directory below, which the App Sandbox's container-relative file access wouldn't permit reaching at all), and `CFBundleIconFile = AppIcon` (`AppIcon.icns`, next to this file, source `assets/app-icon.svg` — without this key the app had no icon resource at all, which is why Notification Center rendered a generic blank circle instead of a real icon next to its banners; now the same shield-checkmark glyph as the Windows Agent's own tray icon and this app's `NSStatusItem`).

## 3. The daemon ↔ menu bar IPC contract

Neither process talks to the other over a socket, XPC, or any Apple IPC primitive — they share a single directory instead: `/Library/Application Support/Applivery/SOAR/`, mirroring the Windows agent's own `%ProgramData%\Applivery\SOAR\` design 1:1.

- **`status.json`** — written by the daemon (root, `0644`) after every report cycle, best-effort and silent on failure (never blocks or fails the report itself over a local write error). Read by the menu bar app (unprivileged) on every panel open plus its own 60s refresh loop.
- **`trigger-report.flag`** / **`trigger-evaluate.flag`** — written by the menu bar app (`IPCPaths.writeTrigger`, an RFC3339 timestamp purely so `cat`-ing the file mid-troubleshoot means something to a human — the daemon never reads the content, only checks existence) when the user clicks "Force report" / "Force evaluate compliance." Polled and consumed by the daemon's `triggerPollInterval` (2s) ticker in `telemetry_macos.go`.

The permissions model is what makes this safe without any daemon-side socket/auth logic at all: the daemon leaves the shared directory `1777` (world-writable + sticky bit) after every write, which lets the unprivileged menu bar app create the two trigger files, while the sticky bit stops it — or any other local process — from deleting or overwriting the root-owned `status.json` out from under the daemon. The menu bar app never creates the directory itself and never needs to; if the daemon has never run, there's nothing to trigger or read yet either.

## 4. LaunchDaemon / LaunchAgent

- **`es.mi-labs.soar.agent.plist`** → `/Library/LaunchDaemons/`, root, runs `/usr/local/bin/applivery-soar-agent` at boot, restarts on crash (`KeepAlive`).
- **`es.mi-labs.soar.menubar.plist`** → `/Library/LaunchAgents/`, loaded per-console-user (`launchctl bootstrap gui/<uid>`), runs `/Applications/Applivery SOAR.app`.

Both are installed and bootstrapped by the `.pkg` installer's `postinstall` script (§5) — including, for the menu bar `LaunchAgent` specifically, an explicit `launchctl asuser <uid> launchctl bootstrap gui/<uid> ...` call for whoever's already logged in at install time, since a plain file drop into `/Library/LaunchAgents/` is only picked up automatically on that user's *next* login otherwise.

## 5. Build & CI (`.github/workflows/build-pkg.yml`)

Runs on `macos-latest` (the only place in this project's tooling with a real Xcode/Swift/`lipo`/`pkgbuild` toolchain):

1. `go build` twice (`GOARCH=arm64` and `GOARCH=amd64`), then `lipo -create` into one universal `/usr/local/bin/applivery-soar-agent` binary — this Mac's own daemon needs to run unmodified on both Apple Silicon and Intel without a separate `.pkg` per architecture (unlike the Windows agent, which ships two separate MSIs since Windows has no `lipo` equivalent).
2. `swift build -c release --arch arm64 --arch x86_64` — a single invocation with two `--arch` flags already emits one universal binary under `.build/apple/Products/Release/`, no separate `lipo` step needed for the Swift side.
3. Wraps that binary into `Applivery SOAR.app` by hand (`mkdir -p Contents/{MacOS,Resources}`, copying the binary, `Info.plist`, `AppIcon.icns`, and the SPM-generated resource bundle for fonts/images), then `codesign --force --deep --sign -` — **ad-hoc signing only**, pending a real Apple Developer ID signing + notarization pipeline. Enough for Gatekeeper to allow launch on the same machine that built it; not yet a substitute for real signing before distributing this build to customer fleets via MDM.
4. `pkgbuild` assembles both the daemon payload (`/usr/local/bin`, `/Library/LaunchDaemons`) and the app-plus-`LaunchAgent` payload into one `Applivery-SOAR-Agent.pkg`, with the `postinstall` script from §4 baked in.
5. On push to `main` only: the `.pkg` is both (a) POSTed straight to the SOAR backend's zero-config ingest endpoint (`POST /api/internal/agent-builds/macos`, `SOAR_AGENT_BUILD_SECRET` shared-secret header — same mechanism as the Windows agent repo, see the SOAR repo's `ARCHITECTURE.md` §9.2) so a customer can download it from **Settings → Applivery SOAR Agent** with zero GitHub token, and (b) published as this repo's rolling `latest` GitHub Release (same tag reused every push), which the backend's secondary GitHub-token-proxied download path falls back to for anyone who already has a token configured.

Every push (including PRs) at least runs steps 1–4 for compile verification; steps 5 only run on push to `main`.

## 6. Testing

There is no local macOS build machine anywhere in this project's own tooling — `go build`/`swift build` on CI (§5) are the sole compile verification for both binaries, and real end-to-end behavior (the report cycle, the IPC contract, notification behavior, panel positioning) has historically been verified by testing an actual built `.pkg` on a real device, not by an automated test suite in this repo. Treat a change here as unverified until it's built by CI and actually exercised on a device — several bugs in this repo's history (the Firewall status parse, the `status.json` `Codable` decode failure, the notification z-order issue) were only ever caught that way, not by a local build.
